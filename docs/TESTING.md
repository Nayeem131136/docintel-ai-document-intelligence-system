# Testing and evaluation

## Automated tests

| Suite | Command | Count |
|---|---|---|
| Backend (Django) | `cd backend && python manage.py test` | 239 |
| Frontend (Vitest + Testing Library) | `cd frontend && npm test` | 31 |

GitHub Actions (`.github/workflows/ci.yml`) runs both suites, the frontend production build and a
"no missing migrations" check on every push and pull request.

What the backend tests cover: file validation (magic bytes, zip/image bombs, size limits), PDF / OCR / image /
Excel / CSV processing, number and date parsing, LLM client behaviour (retries, errors, circuit breaker,
prompt-injection handling) with a fake LLM, anti-hallucination grounding, every validation rule, duplicate
detection, cross-verification, the REST API (authentication, per-user isolation, upload, reprocess, manual
correction, throttling, security headers), background-task idempotency and recovery, search (keyword,
semantic, hybrid, filters, index upkeep), and the evaluation tooling itself.

Tests never call a real LLM or download a model: the LLM is replaced by a fake and the embedder by the
built-in offline one (`EMBEDDING_BACKEND=hashing`, set automatically under `manage.py test`).

### Coverage (measured)

```bash
cd backend
coverage run --source=documents,evaluation manage.py test
coverage report --omit="*/test*,*/tests.py,*/migrations/*"
```

Measured on the final code: **90%** of all application lines; **95%** when the command-line wrappers that
need a real folder of documents (`process_files`, `run_evaluation`, `evaluation/runner.py`) are left out.
`run_evaluation` itself is exercised by running it (below), not by a unit test.

## Evaluation

`docs/EVALUATION_REPORT.md` is generated by the evaluation commands from real measurements; no figure is typed in.

```bash
cd backend
python manage.py generate_eval_dataset --out eval_data --seed 42      # about 70 synthetic files + ground_truth.json
python manage.py run_evaluation --data eval_data --stress-pages 1000 --report ../docs/EVALUATION_REPORT.md
```

It processes the files with the real pipeline in a throw-away database (your own documents are untouched) and
reports field-level precision / recall / F1, invoice detection, validation detection and false alarms,
cross-verification accuracy, keyword / semantic / hybrid search quality, processing time per file type, and
time and memory for a 1000-page PDF.

The report committed in this repository was produced with `--no-llm` (rule-based fallback). Run the same
command with a Groq key configured to measure the LLM path, and replace the report with that run.

### What the first evaluation run found

Running the evaluation on the first version of the rule-based extractor exposed real defects, which were fixed
and covered by regression tests (`EvaluationRegressionTests`):

- The invoice-number pattern could swallow a title line such as `INVOICE` and miss the real `Invoice # ...` label.
- Labels such as `Inv. No.`, `Issued:`, `To:` and a `Billed to:` heading with the name on the next line were not recognised.
- Spreadsheet registers with headers like `Inv #`, `Gross Total` or `Curr` were not recognised as registers, so
  seven invoices per file were lost.

Field recall of the rule-based path on the generated dataset rose from 66% to 96% and wrong values fell from 33 to 1.
